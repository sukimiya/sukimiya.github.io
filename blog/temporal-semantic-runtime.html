1. 背景

对于个人开发者和小团队而言，直接构建或持续运行一个巨大的端到端多模态模型并不一定是最合适的路线。

传统 Multimodal Foundation Model 倾向于：

Camera ─┐
Audio ──┼──→ Large Multimodal Model ──→ Output
Text ───┘

这种架构需要较大的计算资源、内存、训练数据和工程投入，并且大量连续感知数据最终都会进入大型模型。

另一条更适合本地部署、机器人和个人开发者的路线是：

不构建一个理解所有模态的巨大模型，而是构建多个专业感知模型，并通过统一的 Semantic World Model 与 Cognitive Runtime 协作。

即：

Sensors
   ↓
Specialized Perception Models
   ↓
Semantic World Model
   ↓
Temporal Semantic Runtime
   ↓
Attention / Context
   ↓
LLM
   ↓
Intent
   ↓
Action

LLM 不再负责持续“观看世界”。

LLM 只在需要语言理解、复杂推理、规划或未知情况处理时介入。

2. 核心设计原则

整个架构遵循几个基本原则。

2.1 Semantic World Model ≠ LLM Context

World Model 可以包含非常大量的信息，例如：

30 FPS
×
100~500 semantic features
×
多个实体

这些数据用于维持机器对当前世界状态的表示，但不应该直接发送给 LLM。

LLM 只消费经过压缩后的：

Event
Episode
Relevant State
Memory

2.2 Asynchronous by Default

所有感知模型异步运行。

例如：

Face Model        30 FPS
Pose Model        15 FPS
Object Detection  10 FPS
IMU               200 Hz
VAD               realtime
ASR               variable latency
LLM               on demand

不要求所有模型等待同步 Barrier。

所有 Observation 使用统一时间基准：

observed_at
emitted_at
source_sample_id

系统根据时间戳进行 Temporal Alignment。

原则：

Asynchronous by default, temporally aligned by timestamp.

2.3 LLM 不订阅高频 World State

错误方式：

World State
    ↓
30 FPS
    ↓
LLM

正确方式：

World State
    ↓
ΔWorld
    ↓
Temporal Semantic Engine
    ↓
Event
    ↓
Episode
    ↓
Attention
    ↓
LLM

同时 LLM 可以通过 Query API 主动查询 World Model。

因此信息进入 LLM 有两种模式：

PUSH
重要事件主动通知 LLM

PULL
LLM 根据任务查询 World Model

4. Observation IR

所有不同感知模型通过 Adapter 转换成统一 Observation。

例如：

Face Model
    ↓
Face Adapter
    ↓
Observation IR
Pose Model
    ↓
Pose Adapter
    ↓
Observation IR
ASR
    ↓
Speech Adapter
    ↓
Observation IR

基础结构可以设计为：

struct Observation {
    id: ObservationId,

    source: SourceId,
    subject: EntityId,

    source_sample_id: Option<u64>,

    observed_start_ns: u64,
    observed_end_ns: u64,
    emitted_at_ns: u64,

    feature: Feature,
    value: Value,

    confidence: f32,
}

例如：

subject:
    person_1

feature:
    face.mouth.left_corner.raise

value:
    0.82

confidence:
    0.96

Observation 应尽可能描述客观观察，而不是过早进行高级语义判断。

例如：

mouth corners raised

优于：

happy

因为：

Observation
    ↓
Interpretation
    ↓
Cognition

应该保持分层。

5. World State

World State 是系统中心，而不是 LLM。

例如：

World
│
├── entities
│   │
│   ├── person_1
│   │   ├── visible
│   │   ├── position
│   │   ├── face
│   │   ├── pose
│   │   ├── gaze
│   │   └── speech
│   │
│   ├── pet_1
│   │
│   └── cup_1
│
├── relations
│   ├── person_1 near robot
│   ├── cup_1 on table
│   └── person_2 holding phone
│
├── robot
│   ├── pose
│   ├── current_action
│   └── state
│
└── environment

World State 负责回答：

“机器目前认为世界是什么样子的？”

它可以是高频更新的。

但高频 World State 不直接进入 LLM。

6. ΔWorld

Temporal Semantic Runtime 首先计算：

Previous World State
        +
Current World State
        ↓
      ΔWorld

核心问题不是：

世界现在是什么？

而是：

世界发生了什么变化？

例如：

gaze:
elsewhere → robot

产生：

GAZE_TARGET_CHANGED

关系变化：

cup_1:
ON(table)
    ↓
HELD_BY(person_1)

比杯子的 XYZ 坐标变化更有语义价值。

不同 Feature 使用不同 Change Detector。

Continuous

处理：

absolute delta
velocity
acceleration
threshold crossing
trend

Boolean

处理：

false → true
true → false

Enum

处理：

state_A → state_B

Relation

处理：

RelationAdded
RelationRemoved
RelationChanged

同时使用：

Deadband
Hysteresis
Threshold
Debounce

消除无意义的抖动。

7. Event

ΔWorld 本身不等于 Event。

例如：

eye openness:
0.8 → 0.1

不能直接判断：

BLINK

Blink 是一个时间模式：

OPEN
 ↓
CLOSED
 ↓
OPEN

duration < threshold

因此 Event Detector 本质上可以是一个小型状态机。

ΔWorld
   ↓
Temporal Detector
   ↓
Event

例如：

Event {
    type: BLINK

    subject: person_1

    start: 12.100
    end:   12.320

    confidence: 0.96
}

Event Detector 应该插件化：

detectors/
├── blink
├── gaze
├── head_nod
├── head_shake
├── hand_raise
├── hand_wave
├── person_enter
├── person_leave
├── object_pickup
├── object_drop
└── speech

Detector 只订阅自己感兴趣的 Feature。

例如：

eye.openness
    ├── BlinkDetector
    └── EyeClosureDetector

hand.position
    ├── HandRaiseDetector
    └── WaveDetector

避免所有 Detector 每帧运行。

8. Episode

Event 仍然可能过于碎片化。

例如：

12.0 LOOK_AT_ROBOT

12.4 MOUTH_CORNERS_RAISED

13.1 SPEECH_STARTED

13.8 SPEECH("你好")

14.0 HAND_WAVE

这些 Event 很可能属于同一个连续行为。

因此需要：

Event
 ↓
Event Correlator
 ↓
Episode

Episode 根据：

Subject
Target
Temporal proximity
Spatial proximity
Semantic relation

进行关联。

例如：

Episode #381

subject:
    person_1

target:
    robot

start:
    12.0

end:
    14.0

events:
    LOOK_AT_ROBOT
    MOUTH_CORNERS_RAISED
    SPEECH("你好")
    HAND_WAVE

Episode 首先描述：

哪些事情属于同一个连续行为片段。

然后 Interpretation Layer 才可以进一步判断：

possible_intent:
    greeting

confidence:
    0.94

9. Episode 生命周期

Episode 不应该使用简单固定窗口：

每 5 秒 = 一个 Episode

而应该动态：

First related Event
       ↓
Episode OPEN
       ↓
related Event
       ↓
related Event
       ↓
timeout / context change
       ↓
Episode CLOSE

系统同时允许多个 Episode 存在：

Episode Manager

├── #101
│   Human interaction
│
├── #102
│   Object manipulation
│
└── #103
    Robot navigation

新 Event 通过 Episode Matcher 判断加入哪个 Episode。

第一版可以使用简单评分：

score =
    subject_match
  + target_match
  + temporal_proximity
  + spatial_proximity
  + semantic_relation

不需要 LLM。

10. Temporal Semantic Compression

整个架构的关键目标是逐层压缩信息。

Observation
     ↓
World State
     ↓
ΔWorld
     ↓
Event
     ↓
Episode
     ↓
Interpretation
     ↓
Attention
     ↓
LLM

例如一分钟感知可能产生：

270,000 semantic values

经过 ΔWorld：

8,000 meaningful changes

Event Detector：

200 events

Episode Correlator：

15 episodes

Attention：

3 episodes → LLM

具体比例依场景变化。

核心原则是：

绝大多数感知数据永远不需要经过 LLM。

11. Attention

Attention 不应该仅仅判断“有没有 Event”。

应该考虑：

Information Value
    =
Novelty
×
Relevance
×
Confidence
×
Urgency

例如：

person sitting
→
person sitting

Novelty 接近 0：

IGNORE

但：

person standing
→
person suddenly falls

Novelty 与 Urgency 都很高：

ATTENTION

因此认知系统真正关注的是：

ΔWorld

而不是重复描述 World。

12. Push + Pull Cognitive Interface

LLM 不直接订阅 World State。

LLM 通过两种方式获得信息。

PUSH

Attention Engine 主动通知：

PERSON_ENTERED
PERSON_SPOKE
OBJECT_DROPPED
GESTURE_DETECTED

PULL

LLM 可以查询：

get_visible_people()

get_entity(person_1)

get_recent_events(5s)

get_recent_episode(person_1)

get_relation(person_1, robot)

get_objects_held_by(person_1)

inspect_object(object_7)

因此 World Model 更像：

Semantic Database

而不是一个巨大 Prompt。

13. Evidence Chain

语义压缩过程中不能完全丢弃底层依据。

应该保持：

Episode
   ↓ evidence
Event
   ↓ evidence
ΔWorld
   ↓ source
Observation
   ↓ source
Sensor Sample

例如：

Interpretation:
possible_greeting
        │
        ▼
Episode #381
        │
        ├── LOOK_AT_ROBOT
        ├── HAND_WAVE
        └── SPEECH("你好")
                 │
                 ▼
          Observations
                 │
                 ▼
           Sensor Frames

这样可以：

  • Debug；
  • 回放；
  • 重新 Interpretation；
  • 解释系统判断依据；
  • 更换算法重新计算；
  • 训练未来的模型。

14. Domain Semantic Engine

Temporal Semantic Engine 不应该成为一个万能规则系统。

更合理的架构是：

通用 Temporal Semantic Runtime + 可插拔 Domain Semantic Engines

例如：

                    World State
                         │
                       ΔWorld
                         │
       ┌─────────────────┼──────────────────┐
       ▼                 ▼                  ▼
 Human Social          Pet              Mahjong
    Engine            Engine             Engine
       │                 │                  │
       └─────────────────┼──────────────────┘
                         │
                      Episodes
                         │
                         ▼
                   Cognitive Layer

Domain Engine 定义：

什么 Feature 重要

什么 ΔWorld 有意义

什么时间模式构成 Event

哪些 Event 应该组成 Episode

Episode 可以如何 Interpretation

15. Human Interaction Engine

关注：

face
gaze
pose
speech
distance
person ↔ robot relations

检测：

LOOK_AT_ROBOT
APPROACH_ROBOT
HAND_WAVE
SPEECH_TURN
INTERRUPTION

形成：

Human Interaction Episode

16. Pet Interaction Engine

关注：

pet.position
pet.pose
pet.head
pet.tail
pet.vocalization
pet ↔ owner
pet ↔ robot

产生：

PET_APPROACHED
FOLLOWING
VOCALIZATION
PLAY_SEQUENCE

底层动物姿态模型可以随时替换，不影响 Cognitive Runtime。

17. Mahjong Engine

World State：

players
tiles
table
turn
round
relations

摄像头可能每秒产生大量牌的位置变化。

但 Mahjong Engine 将：

tile moved

进一步理解为：

PLAYER_DISCARDED_TILE
PLAYER_DREW_TILE
PLAYER_CLAIMED_TILE

连续 Event 可以形成：

Episode:
player_3 CHI from player_2

因此大量视频数据最终变成少量游戏事实。

18. Desktop / PC Engine

PC 也可以使用同样的模型：

Screen
Accessibility Tree
Mouse
Keyboard
Application State
        ↓
World State
        ↓
ΔWorld
        ↓
Desktop Semantic Engine

例如：

USER_RUN_PROGRAM
        ↓
APPLICATION_ERROR
        ↓
USER_OPEN_TERMINAL

形成：

Episode:

User attempted to run the program
and encountered a missing dependency.

LLM 不需要持续观看整个屏幕视频。

19. 多 Domain 同时运行

多个 Engine 可以共享 World State：

                    World State
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       Social         Desktop        Mahjong
       Engine          Engine         Engine

例如：

Mahjong Engine:

player_2 discarded 5筒

同时：

Human Engine:

person_1 looked toward robot
person_1 said:
"你觉得我要不要碰？"

Context Builder 合并：

Current interaction:

Person 1 is looking toward you and asks:
"你觉得我要不要碰？"

Relevant Mahjong state:

Player 2 just discarded 5筒.
...

然后才交给 LLM。

20. Domain Engine 动态加载

不同环境启用不同认知能力。

客厅：

Human Social     ON
Pet              ON
Mahjong          OFF
Desktop          OFF

发现麻将场景：

load Mahjong Engine

进入电脑工作场景：

load Desktop Engine

因此：

             Cognitive Runtime
                     │
               Context Router
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
     Social       Desktop       Mahjong
     Engine        Engine        Engine

适合本地有限算力环境。

21. Domain Engine 不输出自然语言

Domain Engine 应该产生结构化 Semantic IR。

不要：

"张三刚才打了一张五筒。"

而应该：

Event {
    domain: MAHJONG
    type: TILE_DISCARD

    actor: player_2
    object: tile_5_dot
}

自然语言转换只发生在：

Context Builder

这样整个 Semantic Runtime 不依赖具体 LLM。

25. 第一阶段实现建议

不要一开始实现完整机器人系统。

先验证三个核心数据结构：

WorldDelta v0.1
Event v0.1
Episode v0.1

然后实现四个测试 Case：

Case 1：Blink

验证：

continuous feature
→ temporal pattern
→ Event

Case 2：Hand Wave

验证：

multi-feature motion
→ temporal pattern
→ Event

Case 3：Pick Up Cup

验证：

position changes
→ relation changes
→ Event

Case 4：Greeting

验证：

gaze
+
mouth movement
+
speech
+
hand wave
    ↓
multiple Events
    ↓
Episode

如果这四种情况可以使用同一套：

WorldDelta
Event
Episode
Evidence

表达，那么 Core Runtime 的基本抽象就成立了。

26. 项目的核心定位

这个项目不是：

Another LLM Agent

也不是：

Another ROS Middleware

更不是：

Another Multimodal Foundation Model

它真正解决的是：

Continuous Reality
        ↓
Perception
        ↓
World State
        ↓
ΔWorld
        ↓
Temporal Pattern
        ↓
Event
        ↓
Episode
        ↓
Attention
        ↓
Cognition

换句话说：

把连续、高频、低层的现实世界状态流，转换成稀疏、结构化、具有时间意义的“事情”。

最终形成：

Physical World
      ↓
Perception
      ↓
Semantic World
      ↓
Temporal Semantic Runtime
      ↓
Cognitive Context
      ↓
LLM / Reasoning Model
      ↓
Intent
      ↓
Action
      ↓
Physical World

27. 最终架构思想

传统多模态 AI 的思路更接近：

让一个足够大的模型持续理解整个世界。

Temporal Semantic Runtime 采取另一条路线：

使用多个专业感知模型持续观察世界，用 World Model 保存世界，用 Temporal Semantic Engine 将连续变化压缩成 Event 与 Episode，只把真正值得认知的信息交给 LLM。

因此：

Sensor Data
     ↓
大量 Observation
     ↓
World State
     ↓
少量 meaningful Δ
     ↓
更少的 Events
     ↓
少量 Episodes
     ↓
极少量 Attention Events
     ↓
LLM

这使得个人开发者和小团队有机会利用普通本地硬件构建持续运行的多模态智能系统，而不必直接与大型端到端多模态 Foundation Model 在模型规模上竞争。

项目真正值得长期积累的部分是：

Semantic IR
World Model
Temporal Semantic Runtime
Domain Semantic Engines
Evidence Chain
Attention
Context Builder
Memory

其中最核心的抽象可以总结成一句话：

不要让 LLM 持续观看世界；让系统先把世界发生的变化组织成“事情”，再让 LLM 去理解这些事情。
